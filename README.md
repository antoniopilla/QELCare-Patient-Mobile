**The patient companion to QELCare — appointments, consultation records, medications, health documents, and notifications in a React + Capacitor app, with the clinic's Folio design adapted for phones.**

## Overview

**QELCare Patient** packages the patient portal of the [QELCare Web Platform](https://github.com/antoniopillaiii/QELCare-Website-Multispecialty-Clinic-Management-System) into a Capacitor mobile app. It connects to the same Express + PostgreSQL API used by clinic staff. Android is checked in as a native project; the iOS project is generated by the included GitHub Actions workflow.

The recent Folio UI port brings the website's paper surfaces, pine navigation, brass accents, serif headings, and visit-progress indicators to the existing mobile workflows. Phone layouts use labeled cards, bottom sheets, a drawer, and five bottom navigation tabs. Patient components are maintained as local copies of the web components, with mobile adaptations rather than a shared package.

## Key Features

### Patient appointments & records

- **Dashboard** — next-appointment card with a visit-progress Thread, care shortcuts, latest vitals, notices, and the latest consultation record.
- **Appointments** — Upcoming, History, Book Appointment, and Relatives tabs; specialty/doctor/date/time selection; booking for yourself or someone else; family profile management. Patients can edit or cancel `PENDING` and `RESCHEDULED` requests; confirmed visits require clinic assistance.
- **Visit progress** — a shared Thread shows Requested → Confirmed → In Queue → Payment → Completed, with separate status treatment for interrupted visits.
- **Consultation Records** — read-only doctor-created records with treatment, prescriptions, search, and pagination.
- **Health Records** — Medications and Documents tabs. Add medicines manually or parse prescriptions with AI, review doctor-approval status, view dose schedules and adherence, and mark doses taken or skipped. Add, edit, search, and delete personal health documents; supported reader uploads are PNG, JPG/JPEG, WEBP, and PDF.
- **Document readers** — PDFs are rendered with `pdfjs-dist`, and document/prescription extraction calls the shared backend's OCR endpoints. Extracted fields remain editable before saving.

### Account & notifications

- **Patient self-service** — registration and email OTP verification, password recovery with email/SMS verification options, and patient-only sign-in.
- **Profile Settings** — Profile and Security tabs, photo upload, inline contact edits with OTP verification when required, account status, and password change. A successful password change signs the patient out.
- **Notifications** — an in-app bell with unread/read controls; Android push registration through Firebase Cloud Messaging when configured. Tapping a native notification follows its destination link.
- **Session handling** — patient route guards, a non-patient access screen, and automatic sign-out after 15 minutes of inactivity. Logout attempts to revoke the backend session and remove the device's push registration before clearing local data.

### Mobile interface & tooling

- **Folio design system** — local Newsreader, Inter, and IBM Plex Mono fonts; Lucide icons; shared fields, panels, statuses, loading/empty/error feedback, and reduced-motion styles.
- **Phone navigation** — safe-area-aware topbar, pine drawer, and Dashboard / Appointments / Records / Health / Profile bottom tabs. Tables become labeled cards, and dialogs adapt to bottom sheets on narrow screens.
- **Native branding** — the Android launcher, splash, and system colors use the QELCare Plus mark and paper/pine palette. iOS CI generates its assets from `assets/`.
- **Build checks** — ESLint, JavaScript type checking through TypeScript, a Git-based UI contract audit, and a Windows release-APK script that aligns, signs, and verifies its output.

## Architecture

```text
Patient app (React in a Capacitor WebView)
        │  HTTPS + Bearer JWT
        ▼
QELCare API (Express) ──▶ PostgreSQL
        │
        ├─ Gemini OCR
        ├─ Email / SMS verification
        └─ FCM push notifications
```

`src/App.js` exposes only patient and account routes. `src/utils/auth.js` resolves the API URL, attaches the session token, and handles sign-out. `src/utils/push.js` registers native devices and handles notification taps. The browser preview uses the same components, with native push registration skipped.

## Getting Started

### Prerequisites

- **Node.js 22.12+** and npm: Capacitor 8 requires Node 22+, and the installed Vite 7 requires at least Node 22.12 on that major version.
- A running [QELCare backend](https://github.com/antoniopillaiii/QELCare-Website-Multispecialty-Clinic-Management-System#getting-started), configured with its database and patient endpoints.
- For Android: **JDK 21**, Android Studio/SDK with **Android API 36** and SDK Build Tools. The native project has `minSdk 24` and `compileSdk`/`targetSdk 36`.
- For local iOS builds: a Mac and Xcode. The included workflow provides a hosted macOS build alternative.

### 1. Clone and install

```bash
git clone https://github.com/antoniopillaiii/QELCare-Mobile-Patient.git
cd QELCare-Mobile-Patient
npm install
```

For an existing checkout, run commands from the directory containing this README and `package.json`.

Repository links match this checkout's configured Git remotes. Anonymous checks returned HTTP 404 during this review; access may be restricted or the repositories may have moved. Confirm access and the URL if cloning fails.

### 2. Configure environment

PowerShell:

```powershell
Copy-Item .env.example .env
```

Keep any existing `.env` and edit it instead of overwriting it.

Bash / macOS:

```bash
cp .env.example .env
```

Set `VITE_API_URL` for the intended native build:

| Scenario | Backend URL |
|---|---|
| Android emulator → backend on your computer | `http://10.0.2.2:5001` |
| Real phone → backend on your LAN | Your computer's reachable LAN address and backend port |
| Installed production app | Your deployed HTTPS backend URL |

On a phone, `localhost` refers to the phone itself. Production builds also read the committed `.env.production`, which overrides `.env`; see [Environment Variables](#environment-variables) before building an APK or IPA.

### 3. Run and use the browser preview

```bash
npm run dev
```

Open `http://localhost:3000` and register a patient or sign in with an existing patient account. Use Appointments to request a visit, Consultation Records to read clinic records, Health Records for personal medications/documents, and Profile Settings for account changes. Data-backed flows require the shared API; this repository has no standalone demo backend or seeded login.

In a browser, the API resolver uses the page's host and protocol on port **5001** (for example, `http://localhost:3000` → `http://localhost:5001`), regardless of `VITE_API_URL`. Native builds use the configured URL. See [`src/utils/auth.js`](src/utils/auth.js).

### 4. Check or build web assets

```bash
npm run lint
npm run typecheck
npm run check:contracts
npm run build
npm run preview
```

The build writes `dist/`; preview normally serves it at `http://localhost:4173`. For data-backed preview on that port, set the shared backend's `FRONTEND_URL=http://localhost:4173` and restart it so CORS permits the preview origin. The browser API resolver still uses port 5001.

`check:contracts` compares current source against local `HEAD`, so it needs Git history and does not exercise a live backend. Its final guard requires the entire `backend-patient-mobile-patch/` directory to be unchanged, including its README; documentation edits there also trigger that guard.

## Environment Variables

| Variable | Description |
|---|---|
| `VITE_API_URL` | Native app's backend base URL, embedded during the Vite build. Omit a trailing slash. |
| `REACT_APP_API_URL` | Compatibility alias mapped by `vite.config.js`; used when `VITE_API_URL` is absent. |

The native resolver falls back to `http://10.0.2.2:5001` if no URL is configured. Browser previews use the host/port rule described above.

`.env.production` contains a public backend URL for production builds and CI. Vite gives `.env.production` precedence over `.env`; an environment variable set before starting Vite takes precedence over both. For example, set the target for a Windows release in the current PowerShell session:

```powershell
$env:VITE_API_URL = 'https://your-backend.example'
npm run apk:release
Remove-Item Env:VITE_API_URL
```

Use your actual backend URL. Rebuild and sync after changing it. Client environment values are included in the app bundle; keep database, email, SMS, AI, and FCM service-account credentials on the backend. Configure the backend's CORS origins for the Capacitor app (`capacitor://localhost` / `http(s)://localhost`) and your browser preview.

## Building the Apps

### Android — debug build

On Linux/macOS or a compatible Bash shell, make the checked-in wrapper executable before using the package script:

```bash
chmod +x android/gradlew
npm run apk:debug
```

The wrapper is tracked without Unix execute permission. On Windows PowerShell, build and sync the assets, then invoke the Windows wrapper explicitly:

```powershell
npm run cap:sync:android
Set-Location android
.\gradlew.bat assembleDebug
Set-Location ..
```

This builds the web assets, syncs Android, and assembles `android/app/build/outputs/apk/debug/app-debug.apk`. The Android project is already checked in, so it does not need `cap:add:android` on a normal checkout.

To open the synced project in Android Studio:

```bash
npm run cap:sync:android
npm run cap:open:android
```

### Android — signed release on Windows

```powershell
npm run apk:release
```

[`scripts/build-apk.ps1`](scripts/build-apk.ps1) builds Vite, syncs Capacitor, runs `gradlew.bat assembleRelease`, aligns and signs the unsigned APK, verifies its signature/application ID/alignment and non-debuggable status, then copies it to:

```text
QELCare-APK/qelcare-patient-release.apk
```

The signed original is `android/app/build/outputs/apk/release/app-release.apk`. APK outputs are ignored by Git.

| Build environment variable | Default / purpose |
|---|---|
| `QELCARE_JAVA_HOME` | JDK path; falls back to `JAVA_HOME`, then `C:\Program Files\Java\jdk-21` |
| `QELCARE_ANDROID_SDK` | SDK path; falls back to `ANDROID_SDK_ROOT`, `ANDROID_HOME`, then `%LOCALAPPDATA%\Android\Sdk` |
| `QELCARE_KEYSTORE` | Signing keystore; defaults to `%USERPROFILE%\.android\debug.keystore` |
| `QELCARE_KEY_ALIAS` | Signing alias; defaults to `androiddebugkey` |
| `QELCARE_STORE_PASSWORD` / `QELCARE_KEY_PASSWORD` | Required for a supplied custom keystore; legacy defaults are used only when `QELCARE_KEYSTORE` is unset |

The default path deliberately preserves the developer certificate used by the existing distributed APK and rejects a different local debug certificate. A fresh checkout on another machine must supply a suitable keystore; the script does not create one. Changing signing identity affects updates to an already installed app. The Gradle release variant has no built-in signing configuration; this PowerShell script performs signing afterward.

Native `versionCode` / `versionName` live in [`android/app/build.gradle`](android/app/build.gradle), independently of `package.json`. Check them when preparing a release. Running Gradle directly does not rebuild `dist/`; run `npm run cap:sync:android` first after web changes.

### Android push notifications

Add a Firebase Android app with package name `com.qelcare.patient` and place its `google-services.json` in `android/app/`. The Gradle plugin is conditional: the APK can build without that file, but push remains inactive. Configure FCM credentials on the backend and rebuild/sync the app. See [`PUSH_SMS_SETUP.md`](PUSH_SMS_SETUP.md) for the integration steps.

### iOS — local Mac or hosted build

On a Mac, generate and sync the ignored native project:

```bash
npm run cap:add:ios
npm run cap:sync:ios
npx cap open ios
```

Run `cap:add:ios` only when `ios/` does not already exist. Configure signing, capabilities, and permission usage descriptions in Xcode as needed.

The [`build-ios.yml`](.github/workflows/build-ios.yml) workflow runs on pushes to `main` or manually through GitHub Actions. It uses Node 22 on a macOS runner, builds the web app, generates/syncs iOS, creates branding from `assets/`, adds camera/photo-library usage descriptions and transport settings, and packages an **unsigned** `QELCarePatient-unsigned.ipa` artifact (retained for 30 days). It selects an Xcode workspace or project according to what Capacitor generated.

The artifact requires signing before installation. This workflow does not configure iOS push notifications, APNs credentials, or App Store distribution, and its latest hosted run has not been verified here.

## Known Limitations

- This is a network-backed client. Appointment, record, OCR, OTP, and notification functionality depends on the shared API and its integrations; it has no offline synchronization.
- The JWT is stored in WebView `localStorage`. Client route guards restrict navigation, while the shared API remains responsible for authorization.
- Patient components are local copies, so shared UI/behavior fixes must be reviewed in both repositories. The mobile Folio port preserves the existing patient flows rather than adding staff or public-site workflows.
- The native configuration enables cleartext traffic and Android mixed content for emulator/LAN testing; the Android manifest enables backup, and release builds are not minified.
- The default release script expects the original local developer keystore. Physical-device camera/file-picker/push behavior and current iOS CI success require separate device/hosted validation.
- Appointment statuses are mapped in the UI and must stay compatible with the backend.
- [`backend-patient-mobile-patch/`](backend-patient-mobile-patch/README.md) is a historical reference containing a schema snapshot and an older route/helper. It is not a complete API, and its helper refers to SQL patch files absent from this checkout. Use the current web repository's backend setup instead of applying this snapshot wholesale.
